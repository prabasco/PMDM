    Estructura de un proyecto Android¶

    Un proyecto Android se organiza en módulos. Cada módulo contiene el código fuente, los recursos y la configuración de compilación necesarios para generar una aplicación, biblioteca o funcionalidad concreta.

    Un proyecto sencillo suele tener un único módulo:

    app

    Sin embargo, proyectos más grandes pueden dividirse en varios módulos:

    MyApp
├── app
├── core
├── data
├── feature-login
└── feature-profile

    Esta organización permite separar responsabilidades, reutilizar código y facilitar el mantenimiento de aplicaciones grandes.

    Proyecto y módulo

    No debemos confundir el proyecto Android con el módulo app.

    El proyecto contiene la configuración general y uno o varios módulos. El módulo app es normalmente el encargado de generar la aplicación Android instalable.

    Estructura general¶

    En un proyecto Android moderno podemos encontrar una estructura similar a:

    MyApp/
│
├── app/
│   ├── src/
│   │   ├── main/
│   │   │   ├── java/
│   │   │   │   └── com/ejemplo/myapp/
│   │   │   │       ├── MainActivity.kt
│   │   │   │       └── ...
│   │   │   │
│   │   │   ├── res/
│   │   │   │   ├── drawable/
│   │   │   │   ├── mipmap/
│   │   │   │   ├── values/
│   │   │   │   ├── xml/
│   │   │   │   └── layout/        # Si usamos interfaces XML
│   │   │   │
│   │   │   └── AndroidManifest.xml
│   │   │
│   │   ├── test/
│   │   └── androidTest/
│   │
│   ├── build.gradle.kts
│   └── proguard-rules.pro
│
├── gradle/
│   ├── libs.versions.toml
│   └── wrapper/
│
├── build.gradle.kts
├── settings.gradle.kts
├── gradle.properties
├── gradlew
├── gradlew.bat
└── local.properties

    Kotlin DSL

    En proyectos Android actuales es habitual encontrar archivos:

    build.gradle.kts
settings.gradle.kts

    La extensión .kts indica que la configuración de Gradle está escrita utilizando Kotlin DSL.

    En proyectos anteriores también es habitual encontrar:

    build.gradle
settings.gradle

    escritos utilizando Groovy DSL.

    El módulo app¶

    El módulo:

    app/

    es normalmente el módulo principal de la aplicación.

    Contiene:

    • código Kotlin o Java;
    • recursos;
    • AndroidManifest.xml;
    • configuración de compilación;
    • dependencias;
    • pruebas.

    Su estructura principal es:

    app/
├── src/
├── build.gradle.kts
└── proguard-rules.pro

    La carpeta src¶

    Dentro del módulo encontramos:

    app/src/

    Esta carpeta contiene los diferentes source sets o conjuntos de código fuente.

    Los principales son:

    src/
├── main/
├── test/
└── androidTest/
    Carpeta Función
    main Código y recursos principales de la aplicación
    test Pruebas unitarias ejecutadas normalmente en la JVM
    androidTest Pruebas que necesitan ejecutarse en un dispositivo o emulador Android

    src/main¶

    La mayor parte del desarrollo de la aplicación se realiza dentro de:

    app/src/main/

    Su estructura habitual es:

    main/
├── java/
├── res/
└── AndroidManifest.xml

    Código fuente: java¶

    La carpeta:

    app/src/main/java/

    contiene el código fuente de la aplicación.

    Aunque la carpeta se llame java, puede contener tanto archivos:

    .java

    como:

    .kt

    Por ejemplo:

    java/
└── com/
    └── ejemplo/
        └── myapp/
            ├── MainActivity.kt
            ├── Usuario.kt
            └── Producto.kt

    Kotlin

    Que Android Studio muestre una carpeta llamada java no significa que el proyecto esté desarrollado necesariamente en Java.

    En un proyecto Kotlin encontraremos normalmente archivos .kt dentro de esta carpeta.

    Organización mediante paquetes¶

    El código se organiza mediante paquetes.

    Por ejemplo:

    com.ejemplo.myapp

    En una aplicación sencilla:

    com.ejemplo.myapp/
├── MainActivity.kt
├── Usuario.kt
└── Producto.kt

    En aplicaciones mayores podemos separar el código según su responsabilidad:

    com.ejemplo.myapp/
│
├── data/
│   ├── local/
│   ├── remote/
│   └── repository/
│
├── domain/
│   ├── model/
│   └── repository/
│
├── ui/
│   ├── screens/
│   ├── components/
│   └── theme/
│
├── viewmodel/
│
└── MainActivity.kt

    Esta estructura no es obligatoria. Depende de la arquitectura utilizada en la aplicación.

    Recursos: res¶

    La carpeta:

    app/src/main/res/

    contiene los recursos utilizados por la aplicación.

    Por ejemplo:

    res/
├── drawable/
├── mipmap/
├── values/
├── xml/
└── layout/

    Android procesa estos recursos durante la compilación y genera identificadores que podremos utilizar mediante la clase:

    R

    Por ejemplo:

    R.drawable.logo
R.string.app_name
R.color.primary

    drawable¶

    Contiene imágenes y recursos gráficos.

    res/drawable/

    Por ejemplo:

    drawable/
├── logo.png
├── imagen_perfil.jpg
├── ic_usuario.xml
└── background_button.xml

    Puede contener:

    • PNG;
    • JPG;
    • WebP;
    • gráficos vectoriales XML;
    • shape drawables definidos mediante XML.

    Se utilizan mediante:

    R.drawable.logo

    mipmap¶

    La carpeta:

    res/mipmap/

    se utiliza principalmente para almacenar los iconos de lanzamiento de la aplicación.

    Es habitual encontrar distintas variantes:

    mipmap-hdpi/
mipmap-mdpi/
mipmap-xhdpi/
mipmap-xxhdpi/
mipmap-xxxhdpi/

    Por ejemplo:

    R.mipmap.ic_launcher

    'values'¶

    La carpeta:

    res/values/

    contiene recursos definidos mediante XML.

    Por ejemplo:

    values/
├── strings.xml
├── colors.xml
├── themes.xml
└── dimens.xml

    strings.xml¶

    Contiene textos:

    <resources>

    <string name="app_name">
        Mi aplicación
    </string>

    <string name="bienvenida">
        Bienvenido a Android
    </string>

</resources>

    Desde Kotlin:

    R.string.bienvenida

    colors.xml¶

    Contiene colores:

    <resources>

    <color name="primary">
        #6200EE
    </color>

</resources>

    Desde Kotlin:

    R.color.primary

    themes.xml¶

    Contiene la configuración de los temas visuales de la aplicación.

    En aplicaciones con Jetpack Compose, buena parte de la configuración visual suele definirse directamente mediante Kotlin dentro de:

    ui/theme/

    Por ejemplo:

    ui/
└── theme/
    ├── Color.kt
    ├── Theme.kt
    └── Type.kt

    layout¶

    La carpeta:

    res/layout/

    contiene los archivos XML utilizados para construir interfaces con el sistema tradicional de vistas de Android.

    Por ejemplo:

    layout/
├── activity_main.xml
├── activity_login.xml
└── item_usuario.xml

    Un ejemplo:

    <TextView
    android:id="@+id/txtTitulo"
    android:layout_width="wrap_content"
    android:layout_height="wrap_content"
    android:text="@string/app_name" />

    Desde Kotlin podemos referenciar el layout mediante:

    R.layout.activity_main

    Jetpack Compose

    En una aplicación desarrollada completamente con Jetpack Compose, normalmente no necesitamos archivos XML para definir las pantallas.

    Por este motivo, un proyecto Compose puede no tener la carpeta res/layout/.

    xml¶

    La carpeta:

    res/xml/

    se utiliza para almacenar archivos XML de configuración.

    Puede contener, por ejemplo:

    xml/
├── backup_rules.xml
└── data_extraction_rules.xml

    También puede utilizarse para otras configuraciones específicas de Android.

    AndroidManifest.xml¶

    El archivo:

    app/src/main/AndroidManifest.xml

    describe información fundamental sobre la aplicación.

    En él podemos declarar:

    • componentes de la aplicación;
    • Activity;
    • Service;
    • BroadcastReceiver;
    • ContentProvider;
    • permisos;
    • características requeridas;
    • configuración general de la aplicación.

    Ejemplo:

    <manifest
    xmlns:android="http://schemas.android.com/apk/res/android">

    <uses-permission
        android:name="android.permission.CAMERA" />

    <application
        android:theme="@style/Theme.MyApp">

        <activity
            android:name=".MainActivity"
            android:exported="true">

            <intent-filter>

                <action
                    android:name="android.intent.action.MAIN" />

                <category
                    android:name="android.intent.category.LAUNCHER" />

            </intent-filter>

        </activity>

    </application>

</manifest>

    Pruebas unitarias: test¶

    La carpeta:

    app/src/test/

    contiene las pruebas unitarias locales.

    Estas pruebas normalmente se ejecutan directamente en la JVM y no necesitan un dispositivo Android.

    Ejemplo:

    test/
└── java/
    └── com.ejemplo.myapp/
        └── CalculadoraTest.kt

    Pruebas instrumentadas: androidTest¶

    La carpeta:

    app/src/androidTest/

    contiene pruebas que necesitan el entorno Android.

    Estas pruebas se ejecutan en:

    • un emulador;
    • un dispositivo Android real.

    Se utilizan, por ejemplo, para realizar pruebas de interfaz.

    Configuración Gradle del módulo¶

    Cada módulo dispone de su propia configuración.

    En un proyecto moderno:

    app/build.gradle.kts

    Aquí se configura, entre otras cosas:

    • plugins;
    • namespace;
    • SDK utilizado para compilar;
    • versión mínima de Android;
    • configuración de compilación;
    • dependencias;
    • Jetpack Compose.

    Ejemplo simplificado:

    plugins {
    alias(libs.plugins.android.application)
    alias(libs.plugins.kotlin.android)
}

android {

    namespace = "com.ejemplo.myapp"

    compileSdk = 36

    defaultConfig {

        applicationId = "com.ejemplo.myapp"

        minSdk = 24

        targetSdk = 36

        versionCode = 1

        versionName = "1.0"
    }
}

    Note

    Los valores concretos de compileSdk, minSdk y targetSdk dependen del proyecto y de las versiones de Android utilizadas.

    Dependencias¶

    Las bibliotecas utilizadas por el módulo se configuran también mediante Gradle.

    Por ejemplo:

    dependencies {

    implementation(
        libs.androidx.core.ktx
    )

    implementation(
        libs.androidx.activity.compose
    )

    implementation(
        platform(libs.androidx.compose.bom)
    )
}

    Las dependencias permiten incorporar bibliotecas como:

    • Jetpack Compose;
    • Navigation;
    • Room;
    • Retrofit;
    • Lifecycle;
    • ViewModel;
    • Firebase;
    • Coil.

    libs.versions.toml¶

    En proyectos Android modernos es habitual utilizar un Version Catalog:

    gradle/libs.versions.toml

    Este archivo permite centralizar:

    • versiones;
    • bibliotecas;
    • plugins.

    Por ejemplo:

    [versions]

kotlin = "..."

[libraries]

androidx-core-ktx = {
    module = "androidx.core:core-ktx"
}

[plugins]

android-application = {
    id = "com.android.application"
}

    Después podemos utilizar las referencias desde Gradle:

    implementation(
    libs.androidx.core.ktx
)

    Esto evita repetir versiones y nombres completos de dependencias en diferentes módulos.

    settings.gradle.kts¶

    El archivo:

    settings.gradle.kts

    define aspectos generales de la estructura del proyecto y qué módulos forman parte de él.

    Por ejemplo:

    rootProject.name = "MyApp"

include(":app")

    En un proyecto multimódulo:

    include(":app")
include(":core")
include(":data")
include(":feature-login")

    build.gradle.kts del proyecto¶

    En la raíz podemos encontrar:

    build.gradle.kts

    Contiene configuración compartida a nivel del proyecto.

    No debe confundirse con:

    app/build.gradle.kts

    que configura específicamente el módulo app.

    Por tanto:

    MyApp/
│
├── build.gradle.kts
│
└── app/
    └── build.gradle.kts

    representa dos niveles diferentes de configuración.

    gradle.properties¶

    El archivo:

    gradle.properties

    permite establecer propiedades utilizadas por Gradle durante la compilación.

    Por ejemplo:

    org.gradle.jvmargs=-Xmx2048m
android.useAndroidX=true

    local.properties¶

    El archivo:

    local.properties

    contiene configuración específica del equipo de desarrollo.

    Por ejemplo, puede indicar dónde está instalado el Android SDK:

    sdk.dir=C\:\\Users\\usuario\\AppData\\Local\\Android\\Sdk

    Warning

    local.properties contiene información específica del equipo y normalmente no debe compartirse en Git.

    Gradle Wrapper¶

    Encontraremos también:

    gradlew
gradlew.bat

gradle/
└── wrapper/

    El Gradle Wrapper permite ejecutar el proyecto utilizando la versión de Gradle configurada para ese proyecto.

    En Windows podemos utilizar:

    .\gradlew.bat build

    En Linux/macOS:

    ./gradlew build

    Esto evita que cada desarrollador tenga que instalar manualmente exactamente la misma versión de Gradle.

    Vista Android y vista Project¶

    Android Studio puede mostrar los archivos mediante diferentes vistas.

    La vista:

    Android

    simplifica la estructura real del proyecto y agrupa los archivos por categorías como:

    app
├── manifests
├── kotlin + java
├── res
└── Gradle Scripts

    Esta no es exactamente la estructura física existente en el disco.

    La vista:

    Project

    permite observar una estructura más próxima a la estructura real:

    app/
└── src/
    └── main/
        ├── java/
        ├── res/
        └── AndroidManifest.xml

    Important

    Para comprender correctamente la estructura de un proyecto Android conviene distinguir entre la vista lógica que muestra Android Studio y la estructura física real de carpetas.

    Estructura simplificada en Android Studio¶

    En la vista Android podemos encontrar algo parecido a:

    MyApp
│
└── app
    │
    ├── manifests
    │   └── AndroidManifest.xml
    │
    ├── kotlin + java
    │   └── com.ejemplo.myapp
    │       └── MainActivity.kt
    │
    ├── res
    │   ├── drawable
    │   ├── mipmap
    │   ├── values
    │   └── xml
    │
    └── Gradle Scripts

    Estructura de un proyecto Jetpack Compose¶

    Un proyecto sencillo basado en Kotlin + Jetpack Compose puede tener una estructura similar a:

    MyApp/
│
├── app/
│   │
│   ├── src/
│   │   │
│   │   ├── main/
│   │   │   │
│   │   │   ├── java/
│   │   │   │   └── com/ejemplo/myapp/
│   │   │   │       │
│   │   │   │       ├── MainActivity.kt
│   │   │   │       │
│   │   │   │       └── ui/
│   │   │   │           └── theme/
│   │   │   │               ├── Color.kt
│   │   │   │               ├── Theme.kt
│   │   │   │               └── Type.kt
│   │   │   │
│   │   │   ├── res/
│   │   │   │   ├── drawable/
│   │   │   │   ├── mipmap/
│   │   │   │   ├── values/
│   │   │   │   └── xml/
│   │   │   │
│   │   │   └── AndroidManifest.xml
│   │   │
│   │   ├── test/
│   │   └── androidTest/
│   │
│   ├── build.gradle.kts
│   └── proguard-rules.pro
│
├── gradle/
│   ├── libs.versions.toml
│   └── wrapper/
│
├── build.gradle.kts
├── settings.gradle.kts
├── gradle.properties
├── gradlew
├── gradlew.bat
└── local.properties

    Una diferencia importante respecto a proyectos Android tradicionales es que las pantallas Compose se escriben directamente en Kotlin:

    @Composable
fun PantallaPrincipal() {

    Text(
        text = "Hola Android"
    )
}

    Por tanto, no necesitamos obligatoriamente:

    res/layout/

    para definir la interfaz.

    Resumen¶

    La estructura de un proyecto Android separa diferentes responsabilidades:

    Elemento Función
    app/ Módulo principal de la aplicación
    src/main/ Código y recursos principales
    java/ Código Kotlin y Java
    res/ Recursos de la aplicación
    drawable/ Imágenes y gráficos
    mipmap/ Iconos de lanzamiento
    values/ Textos, colores, temas y otros valores
    layout/ Interfaces XML, si se utiliza View System
    xml/ Archivos XML de configuración
    AndroidManifest.xml Componentes, permisos y configuración de la app
    test/ Pruebas unitarias locales
    androidTest/ Pruebas sobre Android
    app/build.gradle.kts Configuración del módulo
    build.gradle.kts Configuración general del proyecto
    settings.gradle.kts Módulos y configuración del proyecto
    libs.versions.toml Catálogo de versiones y dependencias
    gradle.properties Propiedades de Gradle
    local.properties Configuración local del equipo
    gradlew / gradlew.bat Gradle Wrapper

    La idea fundamental puede resumirse como:

    Proyecto Android
│
├── Código
│   └── Kotlin / Java
│
├── Recursos
│   ├── imágenes
│   ├── textos
│   ├── colores
│   ├── iconos
│   └── layouts XML
│
├── Configuración Android
│   └── AndroidManifest.xml
│
├── Pruebas
│   ├── test
│   └── androidTest
│
└── Compilación y dependencias
    └── Gradle

    Esta separación permite mantener organizada la aplicación y facilita su desarrollo, mantenimiento, pruebas, reutilización y escalabilidad.
